# Selected Jira histories retained locally

The **Retained Jira histories** card in the event-log workspace provides manual, repeatable ingestion of 1–8 already observed Jira issues. It creates a separate local event log and reuses supplied source-event identity append. Existing Jira evidence receipts, ephemeral previews, MCP access and capture settings are unchanged. This is a bounded local connector, not an organization scheduler or tenant inventory crawler.

An administrator must configure both `OWG_JIRA_SOURCE_READ_ENABLED=true` and the separate `OWG_JIRA_RETAINED_INGESTION_ENABLED=true`, plus `OWG_JIRA_HOST`, `OWG_JIRA_CLOUD_ID` and `OWG_JIRA_OAUTH_ACCESS_TOKEN`. Use a provisioned, revocable OAuth 3LO grant for the configured site. The current grant must include the classic `read:jira-work` and `read:jira-user` scopes; `/myself` establishes current account binding. Never put secrets in issue comments, browser fields, URLs or agent arguments. There is no new native credential enrollment or company-wide OAuth approval in this increment. Missing configuration fails closed; simply installing or opening OWG does not enable reads.

Select opaque `owg:r:` references from existing observed Jira evidence, one per line. Confirm selected reads, local retention, and retention of business status labels/source identities separately. Changing the selection clears all confirmations. Creating a profile does not contact Jira. **Read and retain selected histories** explicitly performs a run. Profiles start enabled for manual clicks only; no polling, timer or restart-triggered read exists. Disable stops subsequent reads and invalidates an in-flight run. Disconnect deletes its profile/checkpoint/manifest, while its imported dataset stays until separately deleted. Deleting the dataset also atomically erases its connector event manifest and checkpoint, disables the profile and makes later runs fail; it never silently creates a replacement. Profile configuration/selected references remain until disconnect.

## Data retained and bounds

Only source-reported creation and status changes become events. Creation uses the issue creation timestamp; a generic `updated` time never becomes a status change. A status activity is `Status: <toString>`. Labels are retained business content, displayed literally, not anonymized. Events include the native numeric issue ID, opaque derived history-item IDs and UTC timestamps. Authors, names, email, assignee identities, comments, summaries, descriptions, `historyMetadata` and source URLs are not retained. The before/after status IDs contribute to a one-way item identity, without adding actor data. Status labels are not business rules or verified outcomes.

The connector reads fixed `api.atlassian.com` endpoints. It reconstructs pagination offsets and ignores provider `self`/`nextPage` targets, refuses redirects, checks current site grants before every data request and checks local configuration/scope before and after every HTTP response. Selected references must still resolve to the exact configured site/issues. Response JSON rejects duplicate keys/nonfinite values and is capped at 512 KiB per response. Runs have a 70-second extraction budget, per-request timeout at most eight seconds and a 120-second commit lease. The bounds are eight cases, ten pages per case, at most 100 histories per page and 30 items per history. A provider may return smaller pages, consuming the same ten-page budget. Unsupported or over-budget history refuses the entire run; it is never silently truncated and retained as complete. UTC timestamps must be explicitly offset and within 1900–2100; history times must fall between creation and the source's update fence. Labels are nonblank, control-free and at most 160 characters.

A page must have coherent integer offset, size, total and boolean EOF metadata. The total must stay fixed, histories must have distinct native IDs, selected issues must have distinct numeric IDs, and the issue ID/creation/update fence must remain unchanged before and after its pages. Account identity must remain unchanged across the run. A failed case refuses the entire selected-case batch. These checks detect several forms of page drift, but Jira offset pagination is **not a snapshot guarantee**: equal-count concurrent changes or provider omissions can escape detection. Every result keeps `source_completeness_verified=false`, `business_outcomes_verified=false`, `execution_authorized=false` and `alert_eligible=false`. No automatic alert evaluation or source writes occur.

## Stable identity, reconciliation and recovery

Each profile owns a random source/case namespace and new dataset; it cannot attach to an arbitrary existing log. The configured host/cloud/token and local HMAC key bind the profile to the exact credential configuration. Account ID is HMAC-bound on the first successful retention; neither the token nor raw account ID enters profile/checkpoint metadata. Rotating credentials or the local key requires a newly consented profile; no silent cross-account adoption or inherited checkpoint occurs. Issue-key rename or lost observed scope fails closed. This conservative increment does not automatically migrate profiles, merge cases across profiles or establish cross-app identity.

Every manual run rescans from offset zero. It does not rely on a high-water timestamp or a saved offset for correctness. A source event identity includes numeric issue ID, history ID, status field and before/after IDs, plus an occurrence slot for identical items. Sorting projected items makes slots independent of array order; distinct items in the same history/time survive. Labels and timestamps remain payload: changed payload under an existing identity refuses the batch. If an earlier retained identity disappears, the batch also refuses. Late/backdated insertions are retained on the next successful rescan. Deletions, corrected status IDs, label corrections and timestamp corrections need a separately reviewed reconciliation/update policy; this connector does not rewrite or erase historical retained events automatically. Unsupported non-status items are outside the retained manifest and cannot support completeness claims.

Profile state, per-event payload manifest, account binding and successful checkpoint commit in the **same DuckDB transaction** as the existing imported/appended events, objects, links, source index and append history. A private in-process transaction hook runs before the existing workspace `COMMIT`; HTTP callers cannot supply it. Checkpoint failure rolls back the event batch, including an initial dataset import. A lost acknowledgement after commit can be retried: the saved dataset ID and source-key deduplication prevent a second log or duplicate events. Diagnostics remain best effort after commit, as for ordinary event-log imports. Checkpoint digests are reproducibility checks, not source signatures.

Only one active lease per profile is allowed. A process interrupted past its lease appears as **interrupted** and requires another explicit manual read. Replacing that lease, disabling or disconnecting invalidates old workers at later reads and commit. Lifecycle changes serialize with the actual commit through the workspace lock; an already committed batch remains retained if a later disable/disconnect occurs. Held old responses cannot restore enabled UI state. Remote revocation is checked at read time, not asserted to be atomic with a later local commit. External configuration changes are detected at local guards; administrators should restart the service when changing process environment.

Failed runs preserve the previous successful checkpoint and last-success timestamp, and expose a content-free error code. A 429 sets a bounded retry delay (60–3600 seconds); there is no automatic retry. Error/disabled/interrupted states are not fresh completed source coverage. The workspace still permits explicitly authorized manual analyses over retained data, with the existing privacy/quality limits. It does not certify staffing, causal handoffs, business conformance or ROI.

## Local API and validation

All routes under `/v1/event-log-sources/jira` require a live `OWG-Session` dashboard capability. AI bearer credentials cannot list, create, read, enable, disable or disconnect profiles. JSON bodies have exact fields, strict booleans and a 4 KiB cap; credentials are not accepted in any body.

- `GET /`: configuration readiness and profiles; no source reads.
- `POST /`: `resource_refs`, `confirm_reads`, `confirm_retention`, `confirm_status_labels`.
- `POST /{profile_id}/run`: `confirm_reads: true`.
- `POST /{profile_id}/enabled`: boolean `enabled`, boolean `confirmed` (true required when enabling).
- `DELETE /{profile_id}`: disconnect profile, retaining the dataset.

The route base has no trailing slash in normal requests. Responses use no-store. Source datasets retain the existing dashboard-only analysis/export boundary and source-ID CSV round trip. They do not become broader observed/MCP evidence or synchronize automatically.

Owned fake-provider tests cover pages, late events, multiple items, conflicts/deletions, revocation, rotation, drift, malformed responses, rollback/lost acknowledgements, leases, scope/lifecycle changes and actual authenticated HTTP. The browser exercises selection consent, real API ingestion/replay, workspace analysis, unsafe-looking literal labels, held old responses, disconnect, WCAG and mobile layout. `scripts/benchmark_retained_jira.py 1000 12` checks 96,008 events against a whole-export integer oracle, complete rescan replay and correction refusal; `1000 30` exercises the 240,008 projected-event bound with synthetic small labels. These do not certify live Jira compatibility, a tenant SLA or company production acceptance. A customer-controlled sandbox, real least-scope OAuth setup, native credential UX, tenant scheduling, durable enterprise jobs, automatic correction reconciliation and broader provider coverage remain separate acceptance work under #431/#370.
