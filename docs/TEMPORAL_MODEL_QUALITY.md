# Temporal model quality workspace

The existing in-sample model quality review is complemented by a three-window historical experiment. Provide four increasing UTC boundaries, exact completion labels, one to six noise settings, and a minimum eligible case count. Each case belongs only to the window where its first visible event occurred. Events at the upper boundary do not enter that window. Only completed prefixes with unambiguous ordering and supported length are eligible; excluded cases are counted. Later reopenings do not revise previous eligibility.

Training alone supplies the inductive miner and vocabulary. All activity labels are retained. Validation coverage-adjusted F-score, then simplicity, then lower noise selects one candidate; only this exact net is replayed against the test window. The report includes training and validation metrics, exact test fitting counts, assigned-population fitting bounds, PNML and digest, and source-pinned test evidence pages. It cannot certify generalization, source completeness or business compliance. Repeated experiments after inspecting test outcomes are not sealed holdout tests.

Dashboard: Model quality → Temporal train / validation / test model quality. Review the three windows and candidate scores, download JSON/CSV, download the selected PNML or open it in the existing replay tool. The latter replay is a separate exploratory operation, not the temporal test. Exact test-case pages distinguish fitting, deviating and unknown.

Local dashboard-only POST /v1/event-logs/{log_id}/model-quality/temporal accepts format openworkgraph.temporal-model-quality.v1, boundaries, end_activities, optional noise_levels, minimum_cases and case_type. POST the same path plus /evidence with settings, expected_review_sha256, status, offset and limit. Requests are source-bound and refused when the visible projection/settings change. Retrospective case filters are unsupported. Limits: 250k visible events, 50k cases, 300 distinct variants per window, 120 events per eligible trace, 6 candidate levels, 200k unique replay steps, 250 net nodes, 100 evidence rows per page and one active experiment. No automatic deployment or approval is granted.

Test evidence also includes per-variant token diagnostics (missing/remaining tokens and unknown activities). Unknown activity counts are weighted by distinct cases, not occurrences; a trace containing an unmodeled activity cannot count as fitting even if its token-only fitness is high. The HTTP regression verifies dashboard-only access, exact evidence scope and strict admission.

The original token fitness, precision and F-score remain unchanged. The validation selection criterion is an explicitly labeled heuristic: multiply token fitness by the share of activity occurrences whose labels exist in the model, then take the harmonic mean with precision. Exact weighted unknown occurrence counts and label coverage are reported for every scored population; unknown-label cases cannot disappear from candidate selection. This is not standard token fitness or optimal alignment.
