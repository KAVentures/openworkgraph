# Local Open Work case declarations (bounded foundation)

`server/open_work_case_declarations.py` adds a **disabled-by-default, internal-only** durable owner-declaration ledger for issue #247 Milestone 3. It complements the existing `open_work_reviews` human-reviewed queue, `open_work_model.compose_case_graph` source/observation projection, `record_graph` and `open_work_outcomes.source_operation_receipt`. It does **not** replace them or register a new REST/MCP tool, browser surface, background scan, scheduler or agent runtime.

## Stored facts and provenance

A trusted local caller can explicitly `save_case_declaration` only for an opaque `owg:w:` item already in the local reviewed queue. The caller must supply an **account-bound opaque `owg:scope:` identifier** from its own verified authorization context; this module cannot authenticate a provider or derive the binding itself. It accepts a fixed, non-textual owner-declared `goal_code` (`review_source_state`, `assess_declared_policy`, `verify_operation`), an `expected_outcome_code` (`human_review_recorded`, `source_state_rechecked`, `operation_receipt_reviewed`), and at most eight explicitly declared dependency references to other reviewed cases in the **same scope**. Self-edges, duplicate edges and cycles are rejected. It does not infer obligations or dependencies from clicks, temporal proximity, agent telemetry or a source status.

The stored row includes an exact monotonic `revision`, creation/update/expiry timestamps, opaque refs and codes only. **At save time, expiry is capped by the admitting human review's own expiry and every declared prerequisite's current expiry.** A declaration created later than its review cannot survive the review's original deadline; a dependent declaration cannot outlive an earlier-expiring prerequisite and reappear if that prerequisite is reviewed again. CAS updates may shorten an expiry when a new prerequisite is declared or retention is reduced, but never renew it—even if the dependency is later removed. A lapsed review requires a fresh explicit declaration, not just a renewed review. Write-time expiry/retention pruning also **transitively erases** declarations that depend on an expired or unreviewed prerequisite. It additionally erases dependent chains when a prerequisite row is **missing from the auxiliary ledger or belongs to a different opaque scope**: merely hiding an orphan on reads is insufficient, because re-declaring the missing prerequisite could otherwise resurrect old dependent approvals. This scope-aware closure is checked before inserting any newly declared case, and does not reinterpret a deleted edge as an independent owner-approved obligation. This prevents a later re-declaration of that prerequisite from reviving a dependent whose prior expiry was longer (for example, after a prerequisite's CAS edit shortened its lifetime). The read-time fixed-point filter still suppresses all such dependents before cleanup occurs. It never contains customer text, titles, native provider identifiers, credentials, amounts, source status, provider receipts, workflow observations or free-text instructions. A new declaration requires `expected_revision=0`; every update requires the **current exact revision**. Concurrent writers are serialized by SQLite `BEGIN IMMEDIATE`; stale edits are rejected, not silently merged. **Any successful CAS revision of a prerequisite transactionally erases its transitive dependent declarations**, even if the prerequisite's codes are unchanged: v1 dependencies refer to an opaque case, not a pinned prerequisite revision, so carrying a dependent owner's earlier approval to a different revision would be unsafe. Failed CAS/cycle checks roll back without erasing dependents; unrelated cases remain. Affected owners must explicitly declare fresh dependencies (revision 0), while their independent review requests remain. This is conservative invalidation, not inferred approval, provider verification or a new permission. Deleting a reviewed case deletes its declaration **and all transitively dependent declarations**, rather than silently stripping owner-declared prerequisite edges and presenting previously blocked work as independent. Unrelated declarations remain intact. Owners must explicitly re-declare any replacement graph; a stale revision cannot resurrect a deleted dependent declaration. If the auxiliary ledger is corrupt or unreadable, review deletion instead erases the entire auxiliary ledger rather than leaving a revoked case behind. A missing review suppresses the declaration from reads even if an interrupted cleanup left a row. A dependency is presented only if its own declaration is current and reviewed, **and all of its transitive prerequisites are also current and reviewed**; if A expires while B depends on A and C depends on B, neither B nor C is returned. Unrelated current declarations remain visible. This is a read-time safety filter, not an inferred business-status change or automatic source recheck.

Every read says `source_state=unknown_until_explicit_recheck` and `source_read_performed=false`. Owner-declared expected outcomes are **not** verified outcomes; business obligation, customer outcome and agent execution authorization remain false. An independent fresh provider receipt from `open_work_outcomes` must still be obtained through the existing authorized reader; the ledger neither stores nor grants that authority. No source status or agent execution is cached as truth.

## Lifecycle and security

The local SQLite file lives in the existing private `auth_dir` with mode `0600` on POSIX. It is created **only** by an explicit save of an already reviewed item. Symlinks, non-regular files, unsafe permissions and unsupported schema versions fail closed. Storage is bounded to 50 declarations and a maximum seven-day TTL, further restricted by the user's human-history retention setting; `ephemeral` retention forbids saves and erases the file on read. Existing review removal erases the corresponding declaration and its transitive dependent declarations, and source replacement/disconnect and session-only history-policy cleanup erase the ledger through the existing `clear_review_intentions` lifecycle. Reads never perform provider/network calls or create a database.

This is a **single-installation local foundation**, not a production org/actor-scoped durable graph or a tenant-wide access-control service. The opaque scope must be supplied by an independently trusted account-bound caller; there is intentionally no untrusted API entry point yet. A declaration save checks current review admission and history retention both before opening storage and again inside its SQLite write transaction. If a source disconnect, review deletion or session-only retention switch occurred between those checks, the save fails closed; deterministic tests exercise all three cases. This narrows a stale-snapshot admission race, but does not establish a cross-process atomic fence. Cross-process source-revocation racing a concurrent save is not a distributed transaction: every read still requires a current reviewed item, but full provider-grant epoch fencing and atomic multi-store erasure remain necessary before exposing writes in a company deployment. Source outage, stale/partial/conflicted receipts and customer outcomes stay unknown. Real-provider acceptance, independent business outcome verification, agent uplift and customer pilots remain open.

## Acceptance

`tests/test_open_work_case_declarations.py` covers default-OFF behavior, prior review admission, scope separation, exact-version CAS including concurrent writers, dependency cycles and same-scope checks, multi-hop review removal without silent dependency laundering, disconnect erasure, retention reduction and session-only scrubbing, review-expiry/re-review resurrection prevention, transitive prerequisite expiry, write-time cascade pruning after a shortened expiry and non-renewing CAS edits, storage symlink/permissions, rollback and absence of native/customer content. Two additional synthetic CAS regressions verify A←B←C transitive invalidation on an exact prerequisite revision, unrelated-case survival, stale dependent CAS rejection, failed cyclic-update rollback and same-value revision invalidation. Two synthetic interrupted-ledger/scope-mismatch regressions remove a prerequisite row or alter its stored scope, verify multi-hop dependents remain hidden, then trigger write-time pruning and verify the old dependent revisions cannot reappear. This guards a local auxiliary-store integrity failure, not cryptographic tamper resistance or atomic cross-process source-grant fencing. Existing workflow mapping, Activity, Discovery Mode, REST/MCP, export and provider readers are untouched. These are synthetic/local tests, **not** real-tenant or customer-outcome validation.
