# Local Open Work case declarations (bounded foundation)

\`server/open_work_case_declarations.py\` adds a **disabled-by-default, internal-only** durable owner-declaration ledger for issue #247 Milestone 3. It complements the existing \`open_work_reviews\` human-reviewed queue, \`open_work_model.compose_case_graph\` source/observation projection, \`record_graph\` and \`open_work_outcomes.source_operation_receipt\`. It does **not** replace them or register a new REST/MCP tool, browser surface, background scan, scheduler or agent runtime.

## Stored facts and provenance

A trusted local caller can explicitly \`save_case_declaration\` only for an opaque \`owg:w:\` item already in the local reviewed queue. The caller must supply an **account-bound opaque \`owg:scope:\` identifier** from its own verified authorization context; this module cannot authenticate a provider or derive the binding itself. It accepts a fixed, non-textual owner-declared \`goal_code\` (\`review_source_state\`, \`assess_declared_policy\`, \`verify_operation\`), an \`expected_outcome_code\` (\`human_review_recorded\`, \`source_state_rechecked\`, \`operation_receipt_reviewed\`), and at most eight explicitly declared dependency references to other reviewed cases in the **same scope**. Self-edges, duplicate edges and cycles are rejected. It does not infer obligations or dependencies from clicks, temporal proximity, agent telemetry or a source status.

The stored row includes an exact monotonic \`revision\`, creation/update/expiry timestamps, opaque refs and codes only. It never contains customer text, titles, native provider identifiers, credentials, amounts, source status, provider receipts, workflow observations or free-text instructions. A new declaration requires \`expected_revision=0\`; every update requires the **current exact revision**. Concurrent writers are serialized by SQLite \`BEGIN IMMEDIATE\`; stale edits are rejected, not silently merged. Deleting a reviewed case deletes its declaration and removes incoming dependency references, incrementing affected revisions. A missing review suppresses the declaration from reads even if an interrupted cleanup left a row.

Every read says \`source_state=unknown_until_explicit_recheck\` and \`source_read_performed=false\`. Owner-declared expected outcomes are **not** verified outcomes; business obligation, customer outcome and agent execution authorization remain false. An independent fresh provider receipt from \`open_work_outcomes\` must still be obtained through the existing authorized reader; the ledger neither stores nor grants that authority. No source status or agent execution is cached as truth.

## Lifecycle and security

The local SQLite file lives in the existing private \`auth_dir\` with mode \`0600\` on POSIX. It is created **only** by an explicit save of an already reviewed item. Symlinks, non-regular files, unsafe permissions and unsupported schema versions fail closed. Storage is bounded to 50 declarations and a maximum seven-day TTL, further restricted by the user's human-history retention setting; \`ephemeral\` retention forbids saves and erases the file on read. Existing review removal prunes the corresponding declaration, and source replacement/disconnect and session-only history-policy cleanup erase the ledger through the existing \`clear_review_intentions\` lifecycle. Reads never perform provider/network calls or create a database.

This is a **single-installation local foundation**, not a production org/actor-scoped durable graph or a tenant-wide access-control service. The opaque scope must be supplied by an independently trusted account-bound caller; there is intentionally no untrusted API entry point yet. Cross-process source-revocation racing a concurrent save is not a distributed transaction: every read still requires a current reviewed item, but full provider-grant epoch fencing and atomic multi-store erasure remain necessary before exposing writes in a company deployment. Source outage, stale/partial/conflicted receipts and customer outcomes stay unknown. Real-provider acceptance, independent business outcome verification, agent uplift and customer pilots remain open.

## Acceptance

\`tests/test_open_work_case_declarations.py\` covers default-OFF behavior, prior review admission, scope separation, exact-version CAS including concurrent writers, dependency cycles and same-scope checks, review removal and disconnect erasure, retention reduction and session-only scrubbing, storage symlink/permissions, rollback and absence of native/customer content. Existing workflow mapping, Activity, Discovery Mode, REST/MCP, export and provider readers are untouched. These are synthetic/local tests, **not** real-tenant or customer-outcome validation.
