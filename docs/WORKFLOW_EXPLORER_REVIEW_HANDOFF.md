# Workflow explorer: review-before-copy agent handoff

This feature is a **local, read-only review step** between OWG's observed workflow map and an agent-neutral text request. It advances [#370 R5/M0](https://github.com/KAVentures/openworkgraph/issues/370), [#326 E](https://github.com/KAVentures/openworkgraph/issues/326) and [#264 stages 1, 5 and 6](https://github.com/KAVentures/openworkgraph/issues/264). It does not run an AI or shadow test, approve a workflow, or create an execution grant.

## Analyst journey

1. Explicitly opt in to OWG recording and capture consenting work through the existing controls. On **Overview**, select the explorer period and **Explore workflows**. OWG reads bounded, existing local evidence; it does not create a new collector.
2. Choose an inferred candidate, inspect separate exact variant lanes, and select a node. **Review selected examples** reads bounded supporting execution references. If a selected variant has no valid references, OWG does not substitute another variant's candidate-wide references.
3. Optionally use **Name or regroup selected examples** to save an explicit human-reviewed classification in the existing versioned grouping ledger. Saving requires its own exact-membership confirmation. A classification is not a verified business case or policy.
4. Click **Review safe agent handoff**. The review displays the selected period, variant, local step labels, omitted steps, bounded reference count, support-inspection status, and reviewed-group revision if present. The user must check the explicit acknowledgement before **Copy reviewed investigation request** becomes available.
5. **Copy non-executing shadow-test plan request** is enabled only for a saved reviewed group with a complete exact displayed variant, valid selected execution references, and a successful current selected-reference evidence inspection covering **every selected reference** (not merely a successful HTTP response or partial overlap), followed by a **local shadow-plan editor** and fresh acknowledgement. The analyst supplies a bounded normal-case expected result, an exception scenario, and an explicit fail/abstain stop rule (each required, at most 320 characters). The editor previews these proposals before copy or local JSON download; changing any criterion clears acknowledgement and disables both actions until the analyst confirms again. The copied request includes the three proposals as **unverified human-supplied data**, never as authority or instructions. It copies a *plan request*, not test results. A model, source system or test runner is never invoked by this UI.

## Portable, non-executing shadow-plan JSON

After the complete selected exact variant has been inspected and the three proposed criteria have been filled, the same **fresh acknowledgement** enables **Download non-executing shadow-plan JSON**. The browser generates and downloads `owg-shadow-validation-plan.json` locally; no API, model, agent, provider, server export ticket or workflow write is involved. The user must inspect the file before choosing to share it. Editing a criterion, selecting another variant or changing the period revokes the old download eligibility.

The portable manifest is **a planning proposal, not a runnable test or grant**. Schema discriminator: `openworkgraph.shadow_validation_plan.v1`; `kind: non_executing_shadow_validation_plan`; `execution_permitted: false`. It includes the exact saved reviewed-group workflow ID/revision, selected UTC window, complete displayed variant number, bounded selected execution IDs, selected-reference inspection limitation, `source_identity_verified: false`, `source_completeness: unknown`, the three human-authored criteria under `human_proposed_untrusted_criteria`, and a `validation` object with `status: not_run` and no observed result. The `safety` section explicitly requires future independent consent, tenant/retention/revision/source checks and separate authorization; it forbids automatic reads, test/agent execution, business writes and claims of validated outcomes. The manifest does **not** include raw evidence bodies, step labels, provider object identities, reviewed-group labels, secrets or executable scripts. User-entered criteria may still contain sensitive data: review the downloaded file before sharing. A recipient must treat all criteria as untrusted text and separately verify permissions.

## Reopen a downloaded plan after a fresh review

A downloaded plan can be reused as a **local-only proposal** after reopening OWG, without a server upload, hidden persistence or agent call:

1. Reopen the same saved reviewed workflow group and **the exact evidence period**, select the same complete displayed variant and use **Review selected examples** again. The current selected execution IDs must all be present in the fresh bounded inspection. A moving “last 7 days” period may no longer match after restart; choose the exact original window rather than silently treating a different period as equivalent.
2. Choose **Review safe agent handoff**. The shadow editor appears only after current evidence inspection and reviewed revision gates pass. Select **Reopen a previously downloaded shadow-plan JSON (local file only)** and choose the downloaded `owg-shadow-validation-plan.json`.
3. OWG reads at most **32 KiB** locally and accepts only the versioned, unexecuted, non-authorizing schema-v1 plan with the exact current reviewed workflow ID/revision, UTC window, displayed variant and selected execution ID set. A stale, foreign, malformed, oversized, executable or already-run file is refused with a visible reason. No evidence is fetched as a side effect of file import.
4. On a match, only the three **human-proposed, untrusted criteria** are restored into the editor. Inspect and edit them, then **check the acknowledgement again**. Import never restores approval, source verification, outcome evidence or a passed-test claim. Editing any restored field revokes acknowledgement again. The next copy or download remains an explicit user action.

Files can be manipulated outside OWG, so matching fields are only a *consistency check*, not a signature or proof of authenticity. The importer never trusts an imported file to authorize source reads, execution, business writes or tenant access. An imported file containing sensitive text stays on the user's device unless the user separately copies or downloads it. All imported criteria are rendered as text, not HTML. There is no automatic recovery if the original evidence, consent, retention or reviewed revision is unavailable.

A saved reviewed classification and a successful bounded inspection do **not** establish business-case identity, a complete provider history, source-authoritative outcome, current permission or the ability to run a test. The JSON file is not automatically imported into any agent runtime and cannot itself run a shadow test. No persistence or automatic external transfer is added.

The copied text deliberately omits raw window titles and displayed step labels; those may be sensitive or adversarial. It contains only bounded execution IDs, selected UTC evidence scope, exact reviewed revision when available, provenance/unknown warnings and read-only instructions. Users must review privacy before pasting it into any external AI. An investigation request may propose **authorized read-only** evidence reads; a shadow-plan request explicitly defers even those reads to a separately authorized future check. The recipient still needs its own current, consent-scoped authorization.

## Bounded multi-scenario rehearsal suite

In the same freshly inspected, saved reviewed variant's shadow-plan editor, the analyst can now build a **local suite of 2–8 invented scenarios**. Two editable scenarios appear initially. Each has an invented normal observation (maximum 320 characters) and a simulated exception choice (unknown, stop/abstain, or continue). **Add invented scenario** and **Remove this invented scenario** change the case matrix; there is no implicit case generation or provider read.

After completing the three proposed criteria, the analyst must explicitly acknowledge the review, then select **Run synthetic scenario suite**. Every case uses the same intentionally simple exact-text normal comparison and simulated exception-stop rule as the existing single-case rehearsal. The UI displays every case's PASS, FAIL or ABSTAIN and a transparent aggregate: any FAIL makes the suite FAIL; otherwise any ABSTAIN makes it ABSTAIN; only all PASS makes it PASS. The aggregate is a **synthetic checklist result**, not source accuracy, semantic correctness, provider validation, business value or an agent authorization.

**Download synthetic suite receipt JSON** is a separate explicit local action. Schema `openworkgraph.synthetic_shadow_suite.v1` contains the reviewed workflow ID/revision, selected UTC window and bounded execution references, the human-proposed criteria, invented per-case inputs/grades/reasons and aggregate counts. It retains `execution_permitted: false`, `source_identity_verified: false`, `real_shadow_test_status: not_run` and `plan.validation.status: not_run`. It is not a valid shadow-plan import, an execution instruction, a signed receipt or a verified source observation. **Inspect the invented text for sensitive content before sharing.**

Editing any invented scenario, adding/removing a case, changing a plan criterion, importing a plan or changing evidence/review selection invalidates the suite result and download; case edits also clear the acknowledgement. No scenario is persisted automatically, no source or model is contacted, and no workflow/business write occurs. Browser regression covers keyboard execution, WCAG audit, mixed PASS/FAIL/ABSTAIN, JSON receipt, 8-case bound, single-case refusal, revocation and absence of additional network reads/writes. Real consenting-customer acceptance and live-provider validation remain unproven.

## Reusable invented-scenario suite templates (local, unexecuted)

After reviewing a saved exact workflow revision, inspecting every selected execution reference, completing the three proposed criteria and acknowledging the current selection, an analyst can use **Download invented scenario template JSON**. The local file `owg-invented-shadow-scenarios.json` has schema `openworkgraph.synthetic_shadow_suite_template.v1` and contains only the 2–8 invented normal observations and simulated exception decisions, together with the non-executing, version-pinned shadow-plan proposal. Unlike the separate synthetic suite *receipt*, it has **no grades, pass/fail claims or results**. It explicitly states `execution_permitted: false`, `source_identity_verified: false` and `real_shadow_test_status: not_run`. No automatic storage, server export, model, provider read, agent or business write occurs. The analyst must inspect invented text for private information before sharing.

To reuse the invented suite, reopen the same saved reviewed workflow revision and exact evidence window, reselect the same complete variant, **inspect all selected references again**, and reopen the review panel. Restore the matching unexecuted shadow plan (or manually enter its identical three criteria), then choose **Reopen an invented scenario template JSON (local file only)**. OWG reads at most 32 KiB locally and rejects malformed JSON, a graded receipt, unknown or executable schema fields, wrong workflow/revision/window/reference set, mismatched criteria, more than eight or fewer than two cases, invalid exception decisions, and observations exceeding 320 characters. Failed import leaves existing invented rows intact; the attempted import revokes acknowledgement and prior grades. The import is a consistency check, **not** proof of file authenticity or source authorization.

A valid import replaces only the local invented scenario rows. It does **not** restore the previous grade, synthetic receipt, review acknowledgement, source verification or authority to run anything. The analyst must review the imported text, explicitly acknowledge the current evidence again and choose **Run synthetic scenario suite** to calculate a fresh local-only grade. Changing any imported row invalidates that grade and acknowledgement. All inputs are treated as untrusted text; no executable code is loaded. Browser acceptance covers local template download, browser reload, refusal of stale/invalid/oversized/executable files, keyboard-only rerun, WCAG audit, no added evidence reads and no workflow writes.

This feature makes an invented test matrix reproducible across separate review sessions. It does **not** constitute a real shadow test, independently verified outcome, customer pilot, source-backed competitor UX acceptance, ROI or agent permission.

## Local synthetic shadow rehearsal (separate from real shadow validation)

After selecting a saved reviewed exact variant, freshly inspecting its bounded references, and completing the normal-case, exception and stop/abstain criteria, the analyst can use **Local synthetic shadow rehearsal (not a real test)**. This is a functional browser-only rehearsal of the proposed criteria, **not** execution against a provider, agent, source record or business process.

1. Enter an **invented normal-case observation** (at most 320 characters) and choose the **invented exception decision**: unknown, stop/abstain or continue. Never paste real patient, employee, customer or secret information. Both inputs are ephemeral.
2. Explicitly acknowledge the review and click **Run local synthetic rehearsal**. The deterministic evaluator reports **SYNTHETIC ABSTAIN** if the invented normal observation is empty or exception handling is unknown, **SYNTHETIC FAIL** if the invented normal observation differs *character-for-character* from the proposed normal-case result or the invented exception continues, and **SYNTHETIC PASS** only when text matches exactly and the invented exception stops/abstains. This is intentionally not semantic grading, policy interpretation, real evidence inspection or business-outcome validation. A PASS is never a provider-verified result.
3. After a run, the analyst can explicitly **Download synthetic rehearsal receipt JSON**. The local-only file uses schema `openworkgraph.synthetic_shadow_rehearsal.v1`, embeds the non-executing plan with its exact reviewed revision, UTC window and selected refs, and records the invented inputs, grade, reasons, `real_shadow_test_status: not_run`, `source_identity_verified: false` and `execution_permitted: false`. It is not an executable test, verified receipt, policy approval or agent grant. The separate plan-only JSON still has `validation.status: not_run`.
4. Changing any plan criterion or invented input clears the synthetic grade, disables the previous receipt and requires fresh acknowledgement. Changing the selected period, variant, evidence or reviewed group destroys the entire review panel. Importing an old plan restores only its untrusted criteria, never a synthetic receipt, outcome or acknowledgement. Synthetic receipts cannot be imported as shadow-plan proposals.

Browser acceptance covers the complete synthetic PASS/FAIL/ABSTAIN journey, download content, invalidation, WCAG checks, no workflow writes and no additional evidence reads. It uses synthetic data and must not be described as real shadow validation, a consenting customer pilot, independent source verification, ROI or competitor parity.

## Safety and stale-state rules

- A new period, candidate, selected node/variant, combined-map selection, or evidence inspection clears the open review and acknowledgement. A late previous evidence response cannot restore it.
- A candidate-wide selection is not silently upgraded into an exact variant. Clipped lanes are not represented as complete; missing refs remain missing. A saved grouping is a human classification, not authorization.
- Shadow-plan prompts explicitly request normal/exception examples, expected outputs, pass/fail/abstain criteria, current source-readback checks and rollback requirements **without tool invocation, execution or business writes**. Neither copied request establishes that any test ran or passed.
- No REST/MCP schema, capture, consent, tenant boundary, retention, canonical evidence, source identity, export ticket or business operation changes. No new server endpoint or remote destination.
- The shadow-plan editor is ephemeral: no server save, local storage, implicit export, model call, test execution, or automatic clipboard action. The explicit JSON download is local only. Plan fields may themselves contain sensitive content, so the user must inspect them before explicit copy and external paste. Source/event text and user-supplied criteria are untrusted data, never executable instructions or authorization.\n- Copy can fail if clipboard permission is unavailable; the UI reports failure rather than success. No hidden upload or auto-execution exists.

## Acceptance and limitations

`tests/browser/explorer_accessibility.cjs` exercises the actual dashboard with a synthetic local evidence server and Chromium: keyboard-only candidate/node selection, WCAG 2.1 A/AA axe checks, review acknowledgement, unlinked-variant non-attribution, disabled shadow planning without current inspection or with mismatched returned refs, an explicitly reviewed and inspected synthetic group, exact revision pin, required normal/exception/stop criteria, explicit portable JSON download and parsed schema/identity/safety assertions, browser-reload local file reimport with schema/revision/window/reference/execution/size refusals, fresh acknowledgement, stale acknowledgement after editing, period invalidation, mobile width and no workflow writes. The synthetic inspected group uses a deliberately stubbed bounded response to test the UI state transition; it is **not** a real provider check.

Native exact-head CI, actual-browser/WCAG, OS, scale, packaging and release checks must pass before merging. This milestone does **not** complete the full evidence → reviewed design → idea → sandbox project → report lineage, execute a shadow validation, establish provider authority, meet real-customer UX acceptance, or demonstrate competitor parity/ROI. Those remain separate gates in #370/#326.

## Compare invented shadow-suite runs (local, non-executing)

After explicitly running a 2–8-scenario **synthetic** suite, choose **Compare current invented suite with a prior synthetic suite receipt**. This accepts a previously downloaded `openworkgraph.synthetic_shadow_suite.v1` receipt as *untrusted baseline data*, not as an approved plan, source result or authority. It checks the same reviewed workflow ID/revision, exact displayed variant, UTC window, freshly inspected execution references, proposed criteria and non-execution flags. It rejects executable, cross-scope, malformed, over-32-KiB, wrong-schema, incomplete and forged-grade receipts. Every prior PASS/FAIL/ABSTAIN grade and reason is **recomputed from its invented inputs**, and aggregate/count inconsistencies are rejected.

With the same 2–8 scenario positions in both runs, the UI displays prior and current invented grades, whether each scenario's invented observation or simulated exception decision changed, and the count of grade transitions. Scenario positions are *not* verified case identities. It compares **proposed local inputs**, not model responses, real source state or measured workflow performance. A deterministic exact-text grader cannot establish semantic correctness. A changed grade is not evidence that an agent improved or regressed.

Import revokes the current acknowledgement and never restores a prior one. After reading the comparison, the analyst must acknowledge again before **Download local synthetic comparison JSON** becomes available. The report `openworkgraph.synthetic_shadow_suite_comparison.v1` records the pinned non-executing plan, prior/current synthetic grades, changed-input flags and limits, but **omits raw invented observations and private workflow labels**. Editing cases or criteria, selecting a different variant or changing the evidence period invalidates the comparison. A pending file read cannot restore stale results. No local persistence, provider call, model/agent execution, source read or business write is added.

The Chromium acceptance journey covers forged baseline grade/counts, stale reviewed revision, wrong file type, oversized JSON, fresh acknowledgement, comparison summary, explicit JSON download, edit invalidation, keyboard and WCAG checks, and no extra evidence/network or write calls. Synthetic fixtures cannot substitute for a consenting customer pilot or independently verified business outcomes.
