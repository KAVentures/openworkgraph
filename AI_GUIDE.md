# OpenWorkGraph AI guide

OpenWorkGraph is a workflow-evidence layer. Its job is to capture and preserve factual evidence about how work happened so that the AI the user already uses can understand, analyze, improve, and potentially automate that work.

## Core interpretation rule

Treat OpenWorkGraph observations as evidence. Do the higher-level reasoning yourself.

When other context or tools are available to you — documents, email, repositories, project systems, calendars, enterprise search, prior conversations, APIs, or other connected sources — combine them with the OpenWorkGraph evidence. OpenWorkGraph contributes the missing behavioral context: what the user actually did, in what order, on which work surfaces, and with what observed effort.

Always distinguish:

- **Observed facts**: timestamps, application/window/page identity, source, clicks, scrolls, keypress counts, focus spans, safe UI labels, navigation and other captured events.
- **Derived heuristics**: inferred tasks, task families, repeated sequences, operational summaries and other model-free interpretations generated by OpenWorkGraph.
- **Your inferences**: reconstructed intent, task boundaries, workflow purpose, friction, repeated processes, improvement ideas and automation opportunities.

Derived heuristics are convenience indexes, not ground truth. If a task row conflicts with the richer evidence, prefer the evidence and explain your inference.

## Recommended analysis behavior

1. Reconstruct the workflow chronologically before recommending improvements.
2. Use raw local evidence when it is included; it is the richest captured evidence layer.
3. Use operational/semantic layers as compact indexes and privacy-normalized views, not as replacements for richer evidence when the richer evidence is available.
4. Look for repeated sequences, handoffs, unnecessary switching, repeated checking, waiting, navigation overhead, manual coordination, and other friction.
5. Do not infer effort from foreground duration alone. Prefer engaged time, interaction counts, and the surrounding sequence. A foreground window may have been left open while the user was away, waiting, or thinking.
6. Treat isolated sessions as candidates, not permanent habits. Repeated observations across sessions are stronger evidence of a stable process.
7. Clearly separate what was observed from what you infer about the user's intent.
8. If you recommend an automation, describe the evidence supporting it and use any other connected context/tools available to verify whether the automation is actually useful.

## Browser evidence and the optional browser extension

OpenWorkGraph works without the browser extension. Desktop accessibility and window observation can still provide useful browser workflow evidence such as browser focus, window/page titles where exposed, timing, interactions, and application transitions.

The optional browser extension adds richer browser-native evidence such as hostname/path, page navigation, safe DOM/control semantics, form submission, control changes, and copy/paste occurrence.

Therefore:

- `browser_semantic_events = 0` does **not** mean that no browser work was captured.
- It means that no browser-extension semantic events are present in the analyzed period.
- Browser context may still exist in desktop-derived titles, accessibility labels, interaction events and transitions.
- Use the `source` field and the capture manifest to understand provenance and limitations.

## AI data dictionary

### Timing and effort fields

- `focus_span`: time during which one application/window remained in the foreground.
- `foreground_seconds`: total time the work surface/window was in front.
- `engaged_seconds`: foreground time with recent keyboard, click, or scroll activity. It is an activity estimate, not proof of continuous work.
- `active_input_seconds`: time very close to observed keyboard/mouse input.
- `idle_seconds`: foreground time outside the engagement grace window.
- `keypress_count`: number of keypresses observed. OpenWorkGraph does not store which keys were pressed or the text that was typed.
- `click_count` and `scroll_count`: counts of observed interactions.

Thinking time cannot always be distinguished from inactivity. Use timing as evidence, not as a definitive measurement of cognitive work.

## Capture limits and privacy semantics

- Typed text and individual key identities are not captured.
- Clipboard contents are not captured; only the occurrence of copy/paste may be recorded.
- Screenshots are not part of normal capture/export.
- Browser query strings, URL fragments, and token-like path segments are removed or normalized.
- A target label may be empty when a control did not expose a safe accessibility label or when a long content row was deliberately not copied into the label field.
- Rows marked `Excluded` carry timing/activity only; sensitive application/title/content was intentionally omitted by the active capture policy.
- Amounts, company names, project/deal names, order/reference numbers, document/page titles and other useful workflow context may deliberately remain because they can be necessary to understand the work.

Review rich exports before sharing them outside the intended analysis context.

## Stable privacy tokens

- `PERSON`: an unnamed or deliberately non-linkable person.
- `PERSON_x`: the same pseudonymized person each time that stable token appears.
- `EMAIL_x`, `IBAN_x`, `PAYMENT_CARD_x`, `SENSITIVE_NUMBER_x`, `SECRET_x`: masked values that remain stable within the installation/export context.
- `OCR_REFERENCE_x`: a legacy reference/OCR value that an older version had incorrectly classified as a payment card. The original digits cannot be reconstructed.
- Other identifier tokens such as `PATIENT_ID_x`, `CASE_ID_x`, `ACCOUNT_ID_x` and `ORG_ID_x` are stable pseudonyms for the corresponding identifier type.

## Reading the data layers

### Raw local evidence
The richest captured event stream. Treat this as the primary evidence layer when it is included.

### Operational events / semantic activity
Privacy-normalized and compact representations useful for indexing, scanning and retrieval. They may intentionally contain less detail than raw local evidence.

### Inferred tasks / repeated task families
Model-free heuristic interpretations of captured events. They are not additional observations and should not override the underlying evidence.

### Capture manifest
Describes what evidence sources and capabilities were observed in the export and what was not captured. Use it before drawing conclusions from missing fields.

## Goal when analyzing OpenWorkGraph data

Your job is not merely to summarize the spreadsheet. Use the workflow evidence to understand how the user actually performed work. Combine it with all other context and tools you legitimately have access to. Then identify recurring processes, friction, avoidable switching, repeated checking, handoff problems, and opportunities to improve or automate the workflow.

Do not assume OpenWorkGraph's own inferred task labels are correct. Reconstruct the work from the evidence when needed.
