# OpenWorkGraph AI guide

OpenWorkGraph is a workflow-evidence layer. Its job is to capture and preserve factual evidence about how work happened so that the AI the user already uses can understand, analyze, improve, and potentially automate that work.

## Core interpretation rule

Treat OpenWorkGraph observations as evidence. Do the higher-level reasoning yourself.

When other context or tools are available to you — documents, email, repositories, project systems, calendars, enterprise search, prior conversations, APIs, or other connected sources — combine them with the OpenWorkGraph evidence. OpenWorkGraph contributes the missing behavioral context: what the user actually did, in what order, on which work surfaces, and with what observed effort.

Always distinguish:

- **Observed facts**: timestamps, application/window/page identity, source, clicks, scrolls, keypress counts, focus spans, safe UI labels, navigation, copy/cut/paste behavior, and other captured events.
- **Derived heuristics**: inferred tasks, task families, repeated sequences, operational summaries and other model-free interpretations generated by OpenWorkGraph.
- **Your inferences**: reconstructed intent, task boundaries, workflow purpose, friction, repeated processes, improvement ideas and automation opportunities.

Derived heuristics are convenience indexes, not ground truth. If a task row conflicts with the richer evidence, prefer the evidence and explain your inference.

## Evidence priority

When multiple OpenWorkGraph layers are present, use this order:

1. **RAW local evidence** — primary captured evidence and the preferred reconstruction source.
2. **Operational events / semantic activity** — compact privacy-normalized indexes that help scan and retrieve the evidence.
3. **Inferred tasks / repeated task families / summaries** — heuristic hints only.

Do not simply summarize OpenWorkGraph's inferred-task table. Reconstruct the workflow yourself from raw evidence whenever the raw layer is present.

## Recommended analysis behavior

1. Reconstruct the workflow chronologically before recommending improvements.
2. Use raw local evidence when it is included; it is the richest captured evidence layer.
3. Read `metadata_json` when working from flattened CSV/XLSX rows. Important fields can live there even when they do not have dedicated columns.
4. Use operational/semantic layers as compact indexes and privacy-normalized views, not as replacements for richer evidence when the richer evidence is available.
5. Look for repeated sequences, handoffs, unnecessary switching, repeated checking, waiting, navigation overhead, manual coordination, and other friction.
6. Do not infer effort from foreground duration alone. Prefer engaged time, interaction counts, and the surrounding sequence. A foreground window may have been left open while the user was away, waiting, or thinking.
7. Treat isolated sessions as candidates, not permanent habits. Repeated observations across sessions are stronger evidence of a stable process.
8. Clearly separate what was observed from what you infer about the user's intent.
9. If you recommend an automation, describe the evidence supporting it and use any other connected context/tools available to verify whether the automation is actually useful.
10. Do not invent content, recipients, outcomes, or implementation details when OpenWorkGraph captured only behavior/context. State uncertainty explicitly.

## Browser identity and stable tab context

The browser sensor can add structured page and tab context to the raw event stream:

- `page.hostname` / flattened `page_host`
- sanitized `page.pathname` / flattened `page_path`
- `browser_session_id`
- `tab_id`
- `tab_context_id`

`tab_context_id` is intended to identify one browser tab within one browser runtime. Use it to distinguish switching between tabs from navigation inside the same tab and to reconstruct tab-specific sequences. It is not a permanent cross-browser identity.

A missing browser-extension signal does not erase desktop browser evidence. Window titles, accessibility labels, timing and transitions can still be useful.

## Semantic actions

Raw browser events may include a conservative `semantic_action` and `semantic_action_confidence` in `metadata_json`.

Examples include:

- `send`
- `submit`
- `save`
- `deploy`
- `export`
- `connect`
- `search`
- `create`
- `delete`
- `merge`
- `approve`
- `copy`
- `cut`
- `paste`

Treat `direct_event` confidence as stronger than `label_heuristic`. A label-derived semantic action is an interpretation of a safe control label, not proof of the user's higher-level goal. Verify it against surrounding events.

## Copy/cut/paste and information-transfer evidence

OpenWorkGraph can record copy/cut/paste **behavior without reading or storing clipboard contents**.

Desktop capture can observe Command/Control+C/X/V as privacy-safe behavior signals. Browser capture can observe browser-native copy/cut/paste events. Depending on the workflow, both sensors may record the same action.

Important metadata can include:

- `clipboard_transfer_id`
- `linked_copy_event_id`
- `clipboard_source_observed`
- `clipboard_source_tab_context_id`
- `clipboard_link_age_seconds`
- `evidence_channel`
- `clipboard_change_token`

Use a shared `clipboard_transfer_id` as evidence that a captured copy/cut and paste belong to the same observed transfer. This is especially useful for reconstructing flows such as:

`source app/page → copy → destination app/page → paste → edit → send/save`

Do **not** infer the copied text itself. OpenWorkGraph deliberately does not capture it.

### Duplicate/corroborating events

A browser copy/paste can be observed both by the desktop shortcut sensor and by the browser DOM sensor. When events are near-simultaneous and clearly refer to the same action/context, coalesce them into one logical workflow step rather than counting them twice. Preserve provenance if useful: independent sensors can corroborate that an action occurred.

A paste with no linked observed source means only that the source was not captured in the available evidence. It may have been copied before the session, copied through a context menu in an unsupported native application, or produced by another mechanism.

## Browser evidence and the optional browser extension

OpenWorkGraph works without the browser extension. Desktop accessibility and window observation can still provide useful browser workflow evidence such as browser focus, window/page titles where exposed, timing, interactions, clipboard shortcuts, and application transitions.

The optional browser extension adds richer browser-native evidence such as hostname/path, stable per-runtime tab context, page navigation, safe DOM/control semantics, form submission, control changes, semantic action hints, and browser-native copy/cut/paste occurrence.

Therefore:

- `browser_semantic_events = 0` does **not** mean that no browser work was captured.
- It means that no browser-extension semantic events are present in the analyzed period.
- Browser context may still exist in desktop-derived titles, accessibility labels, interaction events and transitions.
- Use the `source` field and the capture manifest to understand provenance and limitations.

## AI data dictionary

### Timing and effort fields

- `focus_span`: time during which one application/window remained in the foreground.
- `foreground_seconds`: total time the work surface/window was in front.
- `engaged_seconds`: foreground time with recent keyboard, click, or scroll activity. It is an activity estimate, not proof of continuous work.
- `active_input_seconds`: time very close to observed keyboard/mouse input.
- `idle_seconds`: foreground time outside the engagement grace window.
- `keypress_count`: number of keypresses observed. OpenWorkGraph does not store ordinary key identities or the text that was typed.
- `click_count` and `scroll_count`: counts of observed interactions.

Thinking time cannot always be distinguished from inactivity. Use timing as evidence, not as a definitive measurement of cognitive work.

## Capture limits and privacy semantics

- Typed text and ordinary individual key identities are not captured.
- Clipboard contents are not captured; only copy/cut/paste behavior and non-content linkage metadata may be recorded.
- Screenshots are not part of normal capture/export.
- Browser query strings, URL fragments, and token-like path segments are removed or normalized.
- A target label may be empty when a control did not expose a safe accessibility label or when a long content row was deliberately not copied into the label field.
- Rows marked `Excluded` carry timing/activity only; sensitive application/title/content was intentionally omitted by the active capture policy.
- Amounts, company names, project/deal names, order/reference numbers, document/page titles and other useful workflow context may deliberately remain because they can be necessary to understand the work.

Review rich exports before sharing them outside the intended analysis context.

## Stable privacy tokens

- `PERSON`: an unnamed or deliberately non-linkable person.
- `PERSON_x`: the same pseudonymized person each time that stable token appears.
- `EMAIL_x`, `IBAN_x`, `PAYMENT_CARD_x`, `SENSITIVE_NUMBER_x`, `SECRET_x`: masked values that remain stable within the installation/export context.
- `OCR_REFERENCE_x`: a legacy reference/OCR value that an older version had incorrectly classified as a payment card. The original digits cannot be reconstructed.
- Other identifier tokens such as `PATIENT_ID_x`, `CASE_ID_x`, `ACCOUNT_ID_x` and `ORG_ID_x` are stable pseudonyms for the corresponding identifier type.

## Reading the data layers

### Raw local evidence
The richest captured event stream. Treat this as the primary evidence layer when it is included. Read it chronologically and use `metadata_json` as part of the event, not as disposable debug text.

### Operational events / semantic activity
Privacy-normalized and compact representations useful for indexing, scanning and retrieval. They may intentionally contain less detail than raw local evidence.

### Inferred tasks / repeated task families
Model-free heuristic interpretations of captured events. They are not additional observations and should not override the underlying evidence.

### Agent turns / factual context / task evidence
When present, these are regeneratable context indexes linked back to captured source events.

- `agent_turns` identifies observed Send/Run/Generate-style interactions in recognized agentic tools. A turn is an interaction boundary, not proof of the user's higher-level task or of when an agent finished.
- `factual_context_timeline` groups focus-span facts with nearby observed semantic actions and keeps source event IDs. It does not infer goals.
- `task_evidence` links heuristic task rows to evidence windows, observed outcomes, and agent-turn event IDs.
- Same-context agent-submit boundaries may be merged only conservatively when the session, agent surface, non-empty context anchor, and short timing gap agree. Treat the resulting task boundary as heuristic.

For long histories, prefer retrieving the supporting source rows through `get_workflow_trace` rather than trusting these derived indexes alone.

### Capture manifest
Describes what evidence sources and capabilities were observed in the export and what was not captured. Use it before drawing conclusions from missing fields.

## Suggested reconstruction output

When the user asks what their work data means, prefer an output that contains:

- coherent reconstructed tasks with start/end, project, purpose, steps, tools, outcome and confidence;
- repeated workflow families with concrete observed instances;
- information handoffs between tools;
- friction and avoidable switching/checking;
- candidate automation opportunities with a clear boundary between automatable work and required human judgment;
- uncertainties and missing evidence that materially limit the inference.

## Goal when analyzing OpenWorkGraph data

Your job is not merely to summarize the spreadsheet. Use the workflow evidence to understand how the user actually performed work. Combine it with all other context and tools you legitimately have access to. Then identify recurring processes, friction, avoidable switching, repeated checking, handoff problems, and opportunities to improve or automate the workflow.

Do not assume OpenWorkGraph's own inferred task labels are correct. Reconstruct the work from the evidence when needed.
